Development Plan (v2)
A review of the original roadmap, the errors found, and a redesigned, build-ready plan.
1. Verdict
The original plan has a solid skeleton: build the core (index + BM25) from scratch, go
incrementally, and treat privacy as architecture. Keep all three ideas. However, it has real
problems that would hurt you during implementation:
The architecture is drawn as one straight line, but a search engine has two separate
paths (offline ingestion and online querying).
Several technical details are wrong or incomplete (URL normalization, stop words vs
phrase search, IDF formula, score combination, evaluation metrics).
The privacy design has gaps that contradict its own promise (query strings in logs,
Referer leakage, a third-party AI API).
The roadmap contradicts itself (Milestone 1 says start with the index, the phases say
start with the crawler), and the 10-week timeline is optimistic.
Scope option A ("crawl the public internet") is unrealistic for one person.

3. Scope, Goals and Non-Goals
Vision. An independent search engine over a curated set of sites, with transparent
ranking and minimal data collection.
Scope decision (recommended).
v1: Focused public-web crawl (e.g. programming documentation, selected blogs,
Wikipedia subset) plus a static corpus for testing.
v2: Add private documents (PDF, Markdown, text) as a second source type = hybrid
search.
Non-goals for v1: web-scale crawling, JavaScript rendering, personalization, ads,
accounts.
Honest limitation to document: pages that need JavaScript to show content will be
extracted poorly. Say so in the README rather than hiding it.
Naming. Check that "PRIVEX" does not clash with an existing company or product before
you publish. I believe a hosting provider uses a similar name, so verify.

=== PAGE 7 ===
Search nodes never write to the index. They load immutable segments, so reads need
no locks. Index updates swap in a new segment set atomically.
The analyzer is a single package used on both sides. Index/query analyzer mismatch is
the most common cause of "missing" results.
PostgreSQL holds documents, crawl state and links. The index holds the term →
postings structure. Never query Postgres full-text search for ranking.
5. Component Designs
5.1 Crawler (Frontier + Fetcher)
Frontier (Mercator-style)
Front queues by priority (seed depth, sitemap hint, freshness need).
Back queues, one per host, each with a "next allowed fetch time".
A worker pool pulls from whichever host is ready, so one slow site cannot stall
everything.
Persist state in PostgreSQL with lease claiming ( FOR UPDATE SKIP LOCKED ,
lease_expires_at ) so crashes do not lose work.
Fetcher rules
Identify yourself in the User-Agent and honor robots.txt (RFC 9309): cache per
host, treat 5xx as "temporarily disallow", respect Crawl-delay and use Sitemap:
entries.
Default politeness: at most one request per host per second or the declared delay,
and a small per-host concurrency (1–2).
Use conditional requests ( ETag , If-Modified-Since ) for recrawls.
Limits: connect/response timeouts, max body size, max redirects, content-type
allowlist ( text/html , later application/pdf ).
Spider-trap protection: max depth, max URLs per host, ignore calendar/session-ID
URL patterns, cap URL length.
SSRF protection: after DNS resolution, reject loopback, private, link-local and
metadata addresses; re-check on every redirect.
Bounded worker pools with context cancellation and graceful shutdown.

5.2 Extraction
Decode charset to UTF-8 ( golang.org/x/net/html/charset ).
With goquery / x/net/html : remove script , style , noscript , template , nav ,
footer , aside ; collect title , meta description , h1–h3 , body text (join text
nodes with spaces so words do not fuse), links with anchor text, rel=canonical ,
lang .
Main-content heuristic: prefer <main> / <article> ; fall back to text-density scoring.
Output a Document struct with separate fields: title , headings , body ,
url_tokens , anchor_text (from inbound links, added later), plus content_hash of
normalized body text and fetched_at .
Respect <meta name="robots" content="noindex,nofollow"> and X-Robots-Tag .
5.3 Analyzer
Pipeline (applied identically at index and query time):
1. Unicode NFKC normalization and lowercasing.
2. Tokenize on non-letter/non-digit boundaries (keep things like c++ , go1.22 via a small
exception list or a bigram fallback).
3. Record position of every token (before any filtering).
4. Optional stemming (English Snowball) stored as the indexed form; keep the
unstemmed form only if you want exact-match boosts.
5. Stop words are not removed from the index. At query time, drop them only when the
query has enough other terms and no phrase quotes.
5.4 Index and Segment Format
In-memory write buffer
type Posting struct {
    DocID     uint32
    Positions []uint32 // field-tagged positions; tf = len(Positions)
}
// term -> postings sorted by DocID (appended in increasing DocID order)
Immutable on-disk segment
Term dictionary: sorted terms → (document frequency, postings offset). Start with a
sorted file plus binary search; move to an FST later.

=== PAGE 9 ===
Postings file: delta-encoded DocIDs, varint-compressed, with term frequency and
per-field positions. Add skip pointers for long lists later.
Document table: internal DocID → external ID, field lengths (title/headings/body),
total length.
Tombstone bitmap: deleted/replaced documents.
Segment merge: periodically merge small segments (LSM idea) and drop tombstoned
docs.
Global statistics: N, per-field average lengths, per-term DF (summed across
segments) are required for correct BM25.
Use uint32 internal DocIDs mapped to Postgres BIGINT IDs, which halves memory.
Query algorithms
AND: intersect posting lists, shortest first.
Phrase: intersect docs, then check positions with offsets ( pos(t2) = pos(t1)+1 ).
Boolean: AND/OR/NOT through set operations on sorted lists.
Top-k: min-heap of size k; later optimize with WAND/MaxScore.
Default query semantics: try all terms (AND); if fewer than a threshold results, relax
to OR with a coordination boost. State this explicitly in your design doc.
5.5 Ranking
Stage 1 (learning exercise): TF-IDF with tf = 1 + ln(f) and idf = ln(N/df) guarded
against zero.
Stage 2 (production baseline): BM25
idf(t)   = ln(1 + (N - n_t + 0.5) / (n_t + 0.5))
score    = sum over query terms t of
           idf(t) * f * (k1 + 1) / (f + k1 * (1 - b + b * |d| / avgdl))
start with k1 = 1.2, b = 0.75 (tune in 1.2–2.0)
Stage 3: BM25F (fields)
tf~(t,d) = sum over fields F of  w_F * tf_F / (1 - b_F + b_F * len_F / 
avglen_F)
score    = sum over t of idf(t) * tf~ * (k1 + 1) / (k1 + tf~)
initial weights: title 3.0, headings 2.0, anchor 2.0, url 1.5, body 1.0
Stage 4: extra signals (after evaluation harness exists)

8. Evaluation Plan
1. Correctness tests: unit tests for tokenizer, URL normalizer, posting-list intersection,
phrase matching, varint encoding, BM25 scores (hand-computed examples).
2. Reference check: index the same corpus in Lucene/Elasticsearch or Pyserini and
compare top-10 overlap for 50+ queries. Small differences are expected; large ones
signal a bug.
3. Judged query set: 50–100 queries with graded relevance (0–3) for the top results of
each system variant (pooling). Public corpora such as Wikipedia dumps, MS MARCO,
or BEIR datasets give you ready judgments.
4. Metrics: nDCG@10 (primary), MRR, P@10, MAP.
5. Performance: p50/p95/p99 latency, queries/second, index size vs raw text, memory
use, indexing throughput (docs/sec), crawl throughput.
6. Regression rule: each ranking change is accepted only if nDCG@10 does not drop.
7. Always report numbers you measured with the corpus size, never targets as results.
